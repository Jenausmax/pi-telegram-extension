# Дизайн: уведомление о зависании на интерактивном вопросе + ответ из Telegram

**Дата:** 2026-06-30
**Статус:** утверждён (Максимом)
**Автор:** Мартин (с Максимом)
**Ключ задачи:** PTE-7

## Контекст и проблема

Extension `pi-telegram-extension` работает как Telegram-бридж к живой сессии pi (текст, голос,
команды; развёрнут systemd-сервисом на сервере `192.168.88.9`, pi крутится в tmux-сессии `pi`).

**Инцидент 2026-06-30:** агент завис в одном turn'е ~23 часа. Причина — сторонний инструмент
`ask_pro` (расширение **pi-soly**) вызвал блокирующий `ctx.ui.select()` и ждал ответа **в TUI**.
Сообщения пользователя из Telegram уходили в очередь `followUp` через `sendUserMessage` и
**не отвечали** на этот блокирующий вызов. Снаружи бот выглядел «мёртвым»: ничего не присылал и
не реагировал. Разблокировать удалось только вручную — вбив клавиши в tmux (`tmux send-keys`).

Цель: бот должен **предупреждать** пользователя, когда агент завис на интерактивном вопросе, и —
для частого случая — позволять **ответить прямо из Telegram**.

## Ограничения API pi (установлено по исходникам SDK на сервере)

SDK: `@earendil-works/pi-coding-agent`
(`/home/max/.local/share/pi-node/current/lib/node_modules/...`).

- Интерактивный ввод агента идёт через `ctx.ui.select/confirm/input` — **блокирующие** вызовы;
  их реализацию даёт активный режим (TUI). `ask_pro`/`soly_ask_user` (pi-soly) зовут именно их.
- **Отдельного события «открылся интерактивный вопрос» нет.** Но `tool_execution_start`
  срабатывает для любого инструмента (включая `ask_pro`), и в `event.args` лежат вопрос и варианты.
- **Подменить результат инструмента из обработчика нельзя:** `tool_call` → `ToolCallEventResult`
  умеет только `block`/`reason`, без возврата результата (в отличие от `user_bash`, где есть `result`).
- **Хука «заменить реализацию `ctx.ui`» нет** — расширение может только *вызывать* UI.

Вывод: «уведомить» — чисто и надёжно (через `tool_execution_start` + watchdog). «Ответить из
Telegram» штатным API недостижимо → единственный путь — **вбивание клавиш в tmux-сессию pi**
(`tmux send-keys`), как при ручной разблокировке.

## Решение: две фазы

Фаза 1 (уведомление) самостоятельна и низкорисковна. Фаза 2 (ответ из Telegram) — за флагом
конфига, опирается на tmux-релей.

### Архитектура

```
                         pi events
   tool_execution_start ───┐
   tool_execution_end ─────┤
   message_*/turn_* ───────┤ (сброс watchdog-таймера)
                           ▼
                  src/prompt-watch.ts  (чистая логика + автомат состояния)
                     │ formatAskNotification(args) → текст для Telegram
                     │ interpretAnswer(text, pendingAsk) → действия с клавишами
                     │ watchdog: !isIdle && тишина N сек → один сигнал
                     ▼
   pendingAsk state ── влияет на маршрутизацию входящего ──┐
                                                           ▼
   src/bridge.ts (makeIncomingHandler):
     pendingAsk активен && answerFromTelegram?
        да  → sendKeys(...) в tmux  (НЕ sendUserMessage)
        нет → обычный feed() → sendUserMessage
                     ▼
   src/index.ts: проводка событий, инжект sendKeys (child_process tmux), таймер watchdog
```

### Модуль `src/prompt-watch.ts` (новый, чистая логика — тестируется без I/O)

- `formatAskNotification(toolName, args): string` — из `args` интерактивного инструмента собирает
  заметное сообщение:
  > 🟡 **Агент ждёт твой ответ**
  > \<вопрос>
  > 1) ⭐ \<вариант1>
  > 2) \<вариант2>
  > _Ответь номером или текстом._

  Должен пережёвывать форму `ask_pro` (мультивопрос Q1..QN с вариантами) и `soly_ask_user`
  (один вопрос); неизвестную форму — деградирует до «агент задал вопрос, ответь в TUI».
- `interpretAnswer(text, pendingAsk): KeyAction[]` — преобразует ответ пользователя в действия:
  - `1`–`9` → набрать цифру (+ Enter для подтверждения/перехода);
  - `esc`/`отмена`/`cancel` → Escape;
  - произвольный текст → literal-ввод текста + Enter (текстовый ввод / «Other…»).
- Автомат watchdog: `noteEvent()` сбрасывает таймер; `checkStall(now, isIdle)` → нужно ли слать
  сигнал (не idle, тишина ≥ `stallTimeoutSec`, ещё не сигналили в этом залипании).

`KeyAction` — нейтральное описание (`{ type: "literal"|"key", value }`), исполняется инжектируемым
`sendKeys`, чтобы логика не зависела от tmux и тестировалась.

### Состояние `pendingAsk`

`{ tool: string; options: string[]; multi: boolean; since: number } | null`.
Ставится на `tool_execution_start` интерактивного инструмента, снимается на `tool_execution_end`
(по совпадению инструмента/`toolCallId`).

### Фаза 1 — уведомление

- `tool_execution_start`: если `toolName ∈ interactiveTools` → `formatAskNotification` → Telegram,
  выставить `pendingAsk`.
- `tool_execution_end` (тот же инструмент) → снять `pendingAsk`, короткое «✅ принято».
- Watchdog-таймер (интервал ~30 с): если `!ctx.isIdle()` и тишина ≥ `stallTimeoutSec` и сигнал ещё
  не послан → «🟡 Похоже, агент ждёт ввода в TUI — проверь / ответь». Один сигнал на залипание;
  сброс на любом событии агента или возврате в idle. Ловит `confirm`-диалоги и неизвестные случаи.

### Фаза 2 — ответ из Telegram (за флагом `answerFromTelegram`, дефолт `true`)

- В `makeIncomingHandler`: команды (`/stop` и т.п.) обрабатываются **первыми** (чтобы можно было
  прервать). Затем: если `pendingAsk` активен и `answerFromTelegram` → `interpretAnswer` →
  `sendKeys` в tmux-сессию `tmuxSession`; иначе обычный `feed()`.
- После отправки клавиш — эхо «↳ отправил: \<…>». `pendingAsk` снимается на `tool_execution_end`.
- Мультивопросные мастера: каждое сообщение пользователя = один шаг; мастер двигается; состояние
  держится до `tool_execution_end`.
- `sendKeys` инжектируется (в проде — `child_process` → `tmux send-keys -t <session> ...`;
  literal-текст через `-l`). Сессия из конфига (`tmuxSession`, дефолт `"pi"`).
- **Спайк перед реализацией Фазы 2:** на живом TUI подтвердить семантику клавиш пикера
  (выбор цифрой, Enter = переход/submit, Escape = отмена) — закладывается в план.

### Конфиг (блок `telegramBot` в settings.json pi)

| Поле | Тип | Дефолт | Назначение |
|------|-----|--------|------------|
| `interactiveTools` | `string[]` | `["ask_pro","soly_ask_user"]` | Инструменты, считающиеся вопросом к пользователю |
| `stallTimeoutSec` | `number` | `180` | Порог тишины watchdog'а |
| `tmuxSession` | `string` | `"pi"` | Целевая tmux-сессия для релея клавиш |
| `answerFromTelegram` | `boolean` | `true` | Включает Фазу 2 (ответ из чата) |

Все поля опциональны; отсутствие → дефолт. Расширяется `src/config.ts` и его тесты.

### Затрагиваемые файлы

- `src/prompt-watch.ts` — **новый**, чистая логика (формат уведомления, разбор ответа, watchdog).
- `src/prompt-watch.test.ts` — **новый**, unit-тесты логики и watchdog (fake timers).
- `src/index.ts` — проводка `tool_execution_start`/`_end`, таймер watchdog, инжект `sendKeys`,
  передача `pendingAsk` в обработчик.
- `src/bridge.ts` — маршрутизация входящего: при активном `pendingAsk` и включённой Фазе 2 →
  релей клавиш вместо `sendUserMessage`.
- `src/bridge.test.ts` — кейсы маршрутизации (pending → клавиши; не pending → feed; команда раньше).
- `src/config.ts` (+ `config.test.ts`) — новые опциональные поля.

## Тестирование

- vitest, как в проекте. Чистая логика `prompt-watch.ts` — без I/O: `sendKeys` и время инжектятся.
- Кейсы: парсинг `ask_pro` (мультивопрос) и `soly_ask_user` (один вопрос) → текст уведомления;
  деградация неизвестной формы; `interpretAnswer` для цифры/текста/esc; watchdog (тишина → сигнал,
  событие → сброс, idle → без сигнала, без повторного спама); маршрутизация в `bridge`.
- tmux в тестах не вызывается (мок `sendKeys`).

## Границы и риски

- Фаза 1 отгружается и приносит пользу самостоятельно; риск низкий.
- Фаза 2 за флагом — tmux-релей по природе хрупче (вбивание клавиш в TUI). Стартуем с нумерованного
  выбора и текстового ввода; сложные/незнакомые диалоги остаются за TUI (Фаза 1 о них предупредит).
- Watchdog настроен на один сигнал и сброс по событиям — без спама.
- Релей предполагает, что pi всегда живёт в tmux-сессии `tmuxSession` (так и есть по деплою).

## Вне области (YAGNI)

- Полный машинный разбор экрана TUI и универсальный ответ на любой тип диалога.
- Ответ на мультивопросные мастера одним сообщением (делаем пошагово — сообщение = шаг).
- Любые изменения в самом pi-soly.
